# ClaudeOclock — Project Spec for Claude Code

> A desk-side AMOLED display showing both **claude.ai** and **Claude Code**
> usage limits in real time, with custom pixel-art animations that react to
> usage intensity. Built entirely from scratch.
>
> Read this file completely before writing a single line of code.
> Every architectural decision is documented here. When in doubt, refer back.

---

## What this is

ClaudeOclock is a physical desk gadget — an ESP32-S3 microcontroller with an
AMOLED display — that sits on the user's desk and shows how much of their
Claude usage limits they have consumed. It tracks two separate data sources:

1. **claude.ai** — captured by a Chrome extension reading the usage UI
2. **Claude Code** — captured by polling the Anthropic API with the local
   OAuth token (same method the official Claude Code CLI uses internally)

A Python daemon running on the user's Windows PC merges both data sources
and pushes them to the display over Bluetooth Low Energy every 60 seconds.

The display shows animated pixel-art — a custom Claude-orange creature —
that gets progressively more frantic as the user burns through their limits.

---

## Target hardware

**Waveshare ESP32-S3-Touch-AMOLED-2.16**

- MCU: ESP32-S3 with OPI PSRAM
- Display: 480×480 CO5300 AMOLED via QSPI
- Touch: CST9220 capacitive touch via I2C
- PMU: AXP2101 (battery management, power button IRQ)
- IMU: QMI8658 (accelerometer, used for auto-rotation)
- BLE 5.0 + Wi-Fi (only BLE used in this project)
- Comes with enclosure — no 3D printing needed
- LiPo battery header (optional, for wire-free desk use)

**Critical pin assignments:**
```
Display (CO5300 QSPI): CS=12, SCLK=38, SDIO0=4, SDIO1=5, SDIO2=6, SDIO3=7, RST=2
I2C bus (touch + PMU + IMU): SDA=15, SCL=14
Touch (CST9220): INT=11, RST=2 (shared with display), addr=0x5A
PMU (AXP2101): addr=0x34
IMU (QMI8658): addr=0x6B
Button LEFT (GPIO 0):  BOOT button — HID Space key (Claude Code voice PTT)
Button RIGHT (GPIO 18): secondary — HID Shift+Tab (mode toggle)
Button PWR (AXP PKEY): cycles screens / cycles animations on splash
```

**USB-C on this board serves two purposes:**
1. Flashing firmware — plug in once, run the flash command, unplug
2. Power — if no LiPo battery is attached, runs off USB-C permanently

## Data model — the contract between all three components

This is the most critical section. The extension, daemon, and firmware must
all agree on this schema. Never change it without updating all three.

### JSON payload (daemon → ESP32 over BLE, max 512 bytes)

```json
{
  "s":     42,        // Claude Code: 5h session usage % (int 0–100)
  "sr":    180,       // Claude Code: session reset in minutes (int, -1=unknown)
  "w":     71,        // Claude Code: 7d weekly usage % (int 0–100)
  "wr":    2880,      // Claude Code: weekly reset in minutes (int, -1=unknown)
  "st":    "normal",  // Claude Code: status ("normal" | "limited" | "unknown")
  "ai_s":  35,        // claude.ai: session usage % (int 0–100, -1=no data yet)
  "ai_sr": 120,       // claude.ai: session reset in minutes (int, -1=unknown)
  "ai_w":  60,        // claude.ai: weekly usage % (int 0–100, -1=no data yet)
  "ai_wr": 1440,      // claude.ai: weekly reset in minutes (int, -1=unknown)
  "ok":    true       // false only if API call completely failed
}
```

**Rules:**
- Every field must be present in every payload. No optional fields.
- Use -1 for unknown integers. Use "unknown" for unknown strings.
- The firmware displays "---" for any -1 value. Never display a negative number.
- `ok: false` means the Claude Code API poll failed. claude.ai data can still
  be valid. Display both independently.

### Firmware struct (`data.h`)

```c
#pragma once
#include <Arduino.h>

struct UsageData {
    // Claude Code (from Anthropic API rate-limit headers)
    float session_pct;          // 0.0 – 100.0
    int   session_reset_mins;   // -1 = unknown
    float weekly_pct;           // 0.0 – 100.0
    int   weekly_reset_mins;    // -1 = unknown
    char  status[16];           // "normal" | "limited" | "unknown"

    // claude.ai (from Chrome extension via daemon)
    float ai_session_pct;       // 0.0 – 100.0, -1.0 = no data
    int   ai_session_reset_mins;
    float ai_weekly_pct;
    int   ai_weekly_reset_mins;

    bool  ok;                   // API call succeeded
    bool  valid;                // true after first successful parse
};
```

### HTTP payload (Chrome extension → daemon, POST to localhost:47821)

```json
{
  "ai_session_pct":        35,
  "ai_session_reset_mins": 120,
  "ai_weekly_pct":         60,
  "ai_weekly_reset_mins":  1440,
  "timestamp":             1716300000
}
```

Fields not available in the DOM should be sent as -1, not omitted.

## Component 1 — Chrome Extension (`extension/`)

**Purpose:** Read usage data from the claude.ai web UI and forward it to the
local Python daemon every 90 seconds.

**Manifest v3.** Required permissions: `scripting`, `storage`.
Host permission: `https://claude.ai/*`.

### `content.js`

Injected into all `https://claude.ai/*` pages. Runs on `document_idle`.

**What to look for in the DOM (as of May 2026):**
Claude.ai shows usage in the left sidebar. The usage indicator typically
contains text like "X messages left" or shows a progress bar. The exact
selectors are fragile and WILL break when Anthropic updates their frontend.

Strategy — try selectors in order, use first match:
```javascript
// Try these in order until one returns a non-null element:
// 1. data-testid attribute (most stable)
// 2. aria-label containing "usage" or "limit"
// 3. Text content matching /\d+\s*(messages?|tokens?)\s*left/i
// 4. A progress/meter element
```

Extract:
- Current session usage as a percentage (0–100)
- Reset time if shown (convert to minutes)
- Weekly usage if shown

If a value cannot be determined, send -1. Never fabricate or estimate.

**Implementation:**
```javascript
// content.js — runs inside claude.ai pages

const POLL_INTERVAL_MS = 90000;

    // Last verified: May 2026

    let session_pct = -1;
    let session_reset_mins = -1;
    let weekly_pct = -1;
    let weekly_reset_mins = -1;

    // [implementation here — inspect claude.ai DOM and fill in]

    return { ai_session_pct: session_pct,
             ai_session_reset_mins: session_reset_mins,
             ai_weekly_pct: weekly_pct,

function sendToDaemon(data) {
    fetch(`http://localhost:${DAEMON_PORT}/usage`, {
        method: 'POST',

        body: JSON.stringify(data)

}

setInterval(() => sendToDaemon(extractUsage()), POLL_INTERVAL_MS);
sendToDaemon(extractUsage()); // send immediately on page load
```

### `background.js`

Service worker. Minimal — the content script handles the HTTP POST directly.
Background script only needed for the popup status display.

```javascript
// Track last successful daemon contact for popup display
let lastContact = null;
let lastData = null;

chrome.runtime.onMessage.addListener((msg, sender, respond) => {
    if (msg.type === 'DAEMON_STATUS') {
        lastContact = msg.success ? Date.now() : lastContact;
        lastData = msg.data || lastData;
        respond({ lastContact, lastData });
    }
});
```

Simple status indicator:
- Green dot + "Daemon connected" if POST succeeded in last 3 minutes
- Red dot + "Daemon not running" otherwise
- Shows last seen usage values (session %, weekly %)
- Link to open claude.ai

## Component 2 — Python Daemon (`daemon/claudeoclock_daemon.py`)

**Platform: Windows.** Must work on Windows 10/11.
**Dependencies:** `bleak` (BLE), `httpx` (Anthropic API HTTP).
Install via: `pip install bleak httpx`

**The daemon does three things simultaneously:**
1. Runs an HTTP server on `127.0.0.1:47821` receiving claude.ai data from extension
2. Polls the Anthropic API every 60 seconds for Claude Code usage
3. Pushes merged payload to the ESP32 over BLE

### BLE constants

```python
DEVICE_NAME   = "ClaudeOclock"
SERVICE_UUID  = "c1a7d001-c1a7-d001-c1a7-d001c1a7d001"
RX_CHAR_UUID  = "c1a7d001-c1a7-d001-c1a7-d001c1a7d002"  # daemon writes here
TX_CHAR_UUID  = "c1a7d001-c1a7-d001-c1a7-d001c1a7d003"  # firmware ack/nack
REQ_CHAR_UUID = "c1a7d001-c1a7-d001-c1a7-d001c1a7d004"  # firmware refresh req
```

### Anthropic API polling (Claude Code data)

Claude Code stores its OAuth token in:
- Windows: `%APPDATA%\Claude\claude_desktop_config.json` or
  `%USERPROFILE%\.claude\.credentials.json`

Read the token, then make a minimal API call — the rate-limit headers on
the response contain the usage data:

```python
API_URL = "https://api.anthropic.com/v1/messages"
API_HEADERS = {
    "anthropic-version": "2023-06-01",
    "anthropic-beta": "oauth-2025-04-20",
    "Content-Type": "application/json",
    "User-Agent": "claude-code/2.1.5",
    "Authorization": f"Bearer {token}",
}
API_BODY = {
    "model": "claude-haiku-4-5-20251001",
    "max_tokens": 1,
    "messages": [{"role": "user", "content": "hi"}],
}

# Parse these response headers:
# anthropic-ratelimit-unified-5h-utilization  → session_pct (float * 100)
# anthropic-ratelimit-unified-5h-reset        → session_reset (unix timestamp)
# anthropic-ratelimit-unified-7d-utilization  → weekly_pct (float * 100)
# anthropic-ratelimit-unified-7d-reset        → weekly_reset (unix timestamp)
# anthropic-ratelimit-unified-5h-status       → status string
```

Convert reset timestamps to minutes-from-now before putting in payload.

### Token file locations to try (Windows, in order)

```python
CREDENTIAL_PATHS = [
    Path.home() / ".claude" / ".credentials.json",
    Path(os.environ.get("APPDATA", "")) / "Claude" / "claude_desktop_config.json",
    Path.home() / "AppData" / "Roaming" / "Claude" / ".credentials.json",
]
```

Parse each as JSON. Look for `accessToken` key, or nested under
`claudeAiOauth.accessToken`. If none found, log and return None.
Claude Code data fields will be 0 / -1 / "unknown" until token is found.

### HTTP server (thread-safe)

```python
import threading
from http.server import HTTPServer, BaseHTTPRequestHandler
import json

ai_data_lock = threading.Lock()
ai_data = {
    "ai_session_pct": -1,
    "ai_session_reset_mins": -1,
    "ai_weekly_pct": -1,
    "ai_weekly_reset_mins": -1,
}

class UsageHandler(BaseHTTPRequestHandler):
    def do_POST(self):
        if self.path == "/usage":
            length = int(self.headers.get("Content-Length", 0))
            body = self.rfile.read(length)
            try:
                data = json.loads(body)
                with ai_data_lock:
                    ai_data.update({
                        k: data[k] for k in ai_data if k in data
                    })
                self.send_response(200)
            except Exception:
                self.send_response(400)
            self.end_headers()
    def log_message(self, *args): pass  # suppress request logs

def start_http_server():
    server = HTTPServer(("127.0.0.1", 47821), UsageHandler)
    server.serve_forever()

threading.Thread(target=start_http_server, daemon=True).start()
```

**CRITICAL:** HTTP server binds to `127.0.0.1` ONLY. Never `0.0.0.0`.

### Payload builder

```python
def build_payload(cc: dict, ai: dict) -> dict:
    with ai_data_lock:
        ai_snapshot = dict(ai_data)
    return {
        "s":     cc.get("s", 0),
        "sr":    cc.get("sr", -1),
        "w":     cc.get("w", 0),
        "wr":    cc.get("wr", -1),
        "st":    cc.get("st", "unknown"),
        "ai_s":  ai_snapshot["ai_session_pct"],
        "ai_sr": ai_snapshot["ai_session_reset_mins"],
        "ai_w":  ai_snapshot["ai_weekly_pct"],
        "ai_wr": ai_snapshot["ai_weekly_reset_mins"],
        "ok":    cc.get("ok", False),
    }
```

### BLE loop

Use `bleak` with `asyncio`. Same pattern as any BLE central:
1. Scan for device named "ClaudeOclock"
2. Cache BLE address in `%USERPROFILE%\.config\claudeoclock\ble-address.txt`
3. Connect, subscribe to REQ_CHAR_UUID notifications
4. Main loop: poll API every 60s, write payload to RX_CHAR_UUID
5. On disconnect: clear cache, backoff, scan again

On Windows, `bleak` uses the WinRT Bluetooth stack. No extra drivers needed.
BLE address format on Windows is `XX:XX:XX:XX:XX:XX`.

### Windows service / auto-start (`install-windows.bat`)

Register as a Windows Task Scheduler task that runs at login:
```batch
schtasks /create /tn "ClaudeOclock Daemon" /tr "pythonw daemon\claudeoclock_daemon.py" /sc onlogon /f
```

Use `pythonw` (not `python`) so no console window appears.

**CRITICAL — LVGL 9 font patching required after generation:**
`lv_font_conv` outputs LVGL 8 format. In each generated `.c` file:
1. Remove `#if LVGL_VERSION_MAJOR >= 8` / `#endif` guards (keep the contents)
2. In the `lv_font_t` struct at the bottom, remove `.cache` field
3. Add these fields: `.release_glyph = NULL`, `.kerning = NULL`,
   `.static_bitmap_data = true`, `.fallback = NULL`, `.user_data = NULL`
Without this patch, all fonts render invisible. No exceptions.

### Screens

4 screens. Enum:

```c
typedef enum {
    SCREEN_SPLASH      = 0,
    SCREEN_COMBINED    = 1,
    SCREEN_CLAUDE_AI   = 2,
    SCREEN_CLAUDE_CODE = 3,

```

**Cycling order (power button):**
SPLASH → COMBINED → CLAUDE_AI → CLAUDE_CODE → COMBINED (wraps here, skips SPLASH)

**Touch anywhere:** toggles between current screen and SPLASH.

Boot screen is SCREEN_SPLASH.

### SCREEN_SPLASH — Pixel-art animation screen

This is the most visually distinctive screen. A 20×20 grid of colored cells
fills the display, showing custom pixel-art animations of a Claude-orange
creature that reacts to current usage intensity.

**Engine architecture:**

```c
// splash.h
#define GRID 20
// Cell size = min(display_width, display_height) / GRID = 480/20 = 24px
// Canvas = 20*24 = 480×480 — fills the entire display on this board
```

Each animation is a sequence of frames. Each frame is a 20×20 array of
palette indices (0–9). Each animation has its own 10-color RGB565 palette.

**Usage-rate groups:** 4 groups, animations assigned per group:
- Group 0 (idle, 0 %/min): slow, relaxed animations
- Group 1 (normal, low %/min): mild activity animations
- Group 2 (active, medium %/min): energetic animations
- Group 3 (heavy, high %/min): frantic, panicked animations

### ANIMATIONS — Design and Implementation

**All animations are written in C as data arrays. No external files.**
Claude Code must design and implement these entirely in code.

Color palette guidance for the creature:
- Primary body: Claude orange (#d97757 → RGB565: 0xDB6B)
- Highlight: warm cream (#faf9f5 → RGB565: 0xFD3E)
- Shadow/dark: deep orange-brown (#4a2010 → RGB565: 0x4900)
- Eyes: near-black (#1a1008 → RGB565: 0x0800)
- Background: true black (0x0000)
- Accent for effects: white (0xFFFF), blue (0x001F), etc.

**Animations to implement (one C array each in `animations.h`):**

Group 0 — Idle / sleeping (slow frame rate ~300ms/frame):
- `anim_idle_breathe` — creature gently pulses/glows, eyes half-closed
- `anim_idle_blink` — creature sits still, occasionally blinks
- `anim_idle_sleep` — creature with "zzz" floating up, eyes closed

Group 1 — Normal (medium frame rate ~150ms/frame):
- `anim_work_think` — creature with a thought bubble, pondering expression
- `anim_work_type` — creature mimicking typing, bobbing slightly
- `anim_look_around` — creature eyes dart left and right, alert

Group 2 — Active (fast frame rate ~100ms/frame):
- `anim_dance_sway` — creature swaying side to side enthusiastically
- `anim_dance_bounce` — creature bouncing up and down with energy
- `anim_surprise` — creature startled, eyes wide, small jump

Group 3 — Heavy / panicking (very fast ~60ms/frame):
- `anim_panic_spin` — creature spinning/whirling rapidly
- `anim_panic_sweat` — creature visibly stressed, sweat drops flying
- `anim_dance_dj` — creature in full manic DJ mode, arms flailing

**Animation data format:**

```c
// animations.h — generated by Claude Code, do not hand-edit after generation

#pragma once
#include <stdint.h>

typedef struct {
    const char*     name;
    uint8_t         frame_count;
    uint16_t        frame_ms;       // ms per frame
    const uint16_t  palette[10];    // RGB565 colors, index 0 = background
    const uint8_t*  frames;         // frame_count * 400 bytes (20*20 per frame)
} SplashAnim;

// Example palette (ClaudeOclock orange creature):
// 0x0000 = background (black)
// 0xDB6B = primary orange body
// 0xFD3E = cream highlight
// 0x4900 = dark shadow
// 0x0800 = eye color (near black)
// 0xFFFF = white accent
```

### BLE firmware side (`ble.{h,cpp}`)

NimBLE peripheral. Exposes one custom GATT service.

```c
#define DEVICE_NAME     "ClaudeOclock"
#define SERVICE_UUID    "c1a7d001-c1a7-d001-c1a7-d001c1a7d001"
#define RX_CHAR_UUID    "c1a7d001-c1a7-d001-c1a7-d001c1a7d002"  // write
#define TX_CHAR_UUID    "c1a7d001-c1a7-d001-c1a7-d001c1a7d003"  // notify ack
#define REQ_CHAR_UUID   "c1a7d001-c1a7-d001-c1a7-d001c1a7d004"  // notify req
```

Also exposes a BLE HID keyboard service (standard 0x1812) so the LEFT
button functions as a Space key (Claude Code voice PTT) when connected.
Two simultaneous BLE connections: one for HID (OS), one for data (daemon).

Advertising: name "ClaudeOclock" + HID service UUID 0x1812 in primary packet.
Scan response: custom service UUID for daemon discovery.

### HAL (Hardware Abstraction Layer)

All board-specific code lives in `boards/waveshare_amoled_216/`.
`main.cpp`, `ui.cpp`, `ble.cpp`, `splash.cpp` call only HAL functions.
Zero `#ifdef BOARD_*` in any shared file.

HAL interfaces (unchanged from standard pattern):
- `display_hal_init()`, `display_hal_begin()`, `display_hal_draw_bitmap()`,
  `display_hal_set_brightness()`, `display_hal_tick()`, `display_hal_round_area()`
- `touch_hal_init()`, `touch_hal_read(&x, &y, &pressed)`
- `input_hal_init()`, `input_hal_is_held(INPUT_BTN_PRIMARY|SECONDARY)`
- `power_hal_init()`, `power_hal_tick()`, `power_hal_battery_pct()`,
  `power_hal_is_charging()`, `power_hal_pwr_pressed()`
- `imu_hal_init()`, `imu_hal_tick()`, `imu_hal_rotation_quadrant()`
- `board_caps()` → `BoardCaps { width, height, name, button_count, has_* }`

**CO5300 display gotcha:** Cannot rotate via MADCTL. Rotation done by CPU
pixel remapping inside `display_hal_draw_bitmap()`. Use PARTIAL render mode
with strip rotation (40-line strips). This is the same approach used by
established ports of this display — implement it correctly.

**Touch gotcha:** CST9220 needs `setSwapXY(true)` + `setMirrorXY(true, false)`
applied in `touch_hal_init()` for the 2.16" board orientation.

**PSRAM gotcha:** LVGL draw buffers must be allocated from PSRAM:
```c
buf1 = (uint16_t*)heap_caps_malloc(W * BUF_LINES * 2, MALLOC_CAP_SPIRAM);
```
Without `qio_opi` in platformio.ini, PSRAM allocation fails silently.

## Idle / auto-sleep

Screen dims and goes dark after 30 minutes of no input.
- Any button press or touch wakes it
- First press after sleep is consumed as wake-only (no action)
- If USB power is present, never sleeps (configurable in `idle_cfg.h`)
- Fade-out: 400ms. Fade-in: 180ms.

## Usage rate tracking (`usage_rate.{h,cpp}`)

Tracks short-term rate of change in session usage (%/min) to drive animation
group selection. Samples the last N data points (at 60s intervals = last 5
minutes of data). Returns group 0–3.

```c
// Thresholds (tune after testing):
// Group 0 (idle):   rate < 0.1 %/min
// Group 1 (normal): rate 0.1–0.5 %/min
// Group 2 (active): rate 0.5–2.0 %/min
// Group 3 (heavy):  rate >= 2.0 %/min
```

On splash screen: when group changes, switch to an animation from the new group.
On combined/detail screens: the spinner animation text speed increases with group.

## `main.cpp` structure

```
setup():
  Serial.begin(115200)
  board_init()           // Wire.begin + any pre-init
  display_hal_init()
  display_hal_begin()
  idle_init()
  power_hal_init()
  imu_hal_init()
  touch_hal_init()
  lv_init() + display/input setup
  ble_init()
  input_hal_init()
  ui_init()
  ui_show_screen(SCREEN_SPLASH)

loop():
  idle_tick()
  lv_timer_handler()
  ui_tick_anim()
  ble_tick()
  power_hal_tick()
  imu_hal_tick()
  splash_tick()
  if (!idle_is_asleep()) display_hal_tick()

  // Button handling:
  // LEFT (GPIO 0): short press → HID Space; long press (>1.5s) → SCREEN_BLUETOOTH
  // RIGHT (GPIO 18): short press → HID Shift+Tab
  // PWR (AXP PKEY): press → cycle screens; on SPLASH → cycle animations

  // BLE data:
  if (ble_has_data()) {
      parse_json(ble_get_data(), &usage);
      usage_rate_sample(usage.session_pct);
      update_anim_group_if_changed();
      ui_update(&usage);
      ble_send_ack();
  }

  delay(5);
```

## Critical rules — never violate these

1. **No `#ifdef BOARD_*` in shared code.** All board code in `boards/<name>/`.
2. **HTTP server binds to `127.0.0.1` only.** Never `0.0.0.0`.
3. **Thread safety.** `ai_data` dict always accessed under `ai_data_lock`.
4. **-1 means unknown, not zero.** Firmware must display "---" not "0%" or "-1%".
5. **LVGL 9 font patch is mandatory.** Unpatch fonts render invisible.
6. **OPI PSRAM required.** `qio_opi` in platformio.ini, or screen is black.
7. **pioarduino platform required.** Do not use standard `espressif32`.
8. **CO5300 cannot rotate via MADCTL.** CPU pixel remapping only.
9. **Extension selector is fragile.** Document the selector in a comment.
   When it breaks, only the selector string changes — nothing else.
10. **Do not store or log OAuth tokens, cookies, or session data** beyond
    what's needed for the API call. The token is read fresh each poll.
11. **Animations are code, not files.** Everything lives in `animations.h`.
    No file I/O, no SD card, no network fetch for animation data.
12. **`animations.h` is fully self-contained.** Must compile with zero
    external dependencies beyond `<stdint.h>`.
